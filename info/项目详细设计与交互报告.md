# 东软颐养中心管理系统项目详细设计与交互报告

## 1. 项目概述

本项目是一个基于 Java 控制台的东软颐养中心管理系统，主要面向养老院后台业务管理场景。系统没有使用数据库，也没有使用 Web 框架，所有数据通过 Java IO 流读写本地 JSON 文件完成持久化。项目采用典型分层结构，将数据对象、数据访问、业务逻辑、控制台菜单交互和公共工具拆分到不同包中，便于维护和扩展。

项目入口类是 `com.neuedu.tms.Main`。程序启动后先进入登录界面，用户输入账号和密码后由 `UserService` 调用 `UserDao` 校验身份。登录成功后根据用户角色跳转到不同菜单：管理员进入 `AdminMainView`，健康管家进入 `StewardMainView`。管理员负责系统基础数据维护、客户管理、床位管理、护理管理、外出审核、退住审核、膳食管理和用户管理；健康管家负责查看自己的服务对象、录入日常护理、查询护理记录、提交外出申请和退住申请。

系统整体围绕“客户入住、床位使用、护理服务、健康管家服务、外出退住审批”展开，核心不是单纯增删改查，而是多个 JSON 数据文件之间的业务状态同步。例如客户入住时需要同时写入客户数据、修改床位状态、生成床位使用详情；退住审核通过时需要更新退住记录、释放床位、结束床位使用记录；日常护理完成后需要新增护理记录并扣减客户护理服务剩余次数。

## 2. 技术架构

项目采用 Maven 管理，`pom.xml` 中配置了 Java 8 编译版本和 Jackson 依赖。Jackson 用于 JSON 文件与 Java 对象之间的转换，JUnit 作为测试依赖，Lombok 依赖虽然存在，但当前实体类整体仍以手写 getter、setter、构造方法和 `toString` 为主。

项目主要包结构如下：

| 包名 | 作用 |
| --- | --- |
| `com.neuedu.tms` | 程序入口，包含 `Main` 类 |
| `com.neuedu.tms.pojo` | 实体类，对应业务数据表或 JSON 数据结构 |
| `com.neuedu.tms.dao` | 数据访问层，每个 DAO 负责一个或一类 JSON 文件的读写 |
| `com.neuedu.tms.service` | 业务逻辑层，负责校验、跨 DAO 调用和状态同步 |
| `com.neuedu.tms.view` | 控制台视图层，负责菜单展示、输入接收和调用 Service |
| `com.neuedu.tms.enums` | 状态枚举，用数字状态映射中文含义 |
| `com.neuedu.tms.utils` | 公共工具类，包括输入、JSON 读写、ID 生成、排序等 |

架构调用方向是：

```text
Main
  -> LoginView
      -> UserService
          -> UserDao
              -> data/user.json

登录成功后：
AdminMainView / StewardMainView
  -> 各业务 View
      -> 对应 Service
          -> 一个或多个 DAO
              -> data/*.json
```

View 层不直接读写 JSON 文件，也不直接修改实体之间的复杂关系；DAO 层不处理复杂业务规则，只负责数据读取、筛选、写回；Service 层是业务一致性的核心，负责把多个 DAO 的操作组合成一个完整业务动作。

## 3. 数据持久化设计

系统使用 `data` 目录下的 JSON 文件保存数据。每个 JSON 文件可以理解为数据库中的一张逻辑表，但实际存储方式是本地文件。

| JSON 文件 | 对应实体 | 主要作用 |
| --- | --- | --- |
| `user.json` | `User` | 保存管理员、健康管家等系统用户 |
| `role.json` | 角色数据 | 保存系统角色信息 |
| `customer.json` | `Customer` | 保存入住客户基础信息 |
| `room.json` | `Room` | 保存房间信息 |
| `bed.json` | `Bed` | 保存床位状态和所属房间 |
| `beddetail.json` | `BedDetail` | 保存客户床位使用历史 |
| `backdown.json` | `Backdown` | 保存退住申请和审核记录 |
| `outward.json` | `Outward` | 保存外出申请、审核和回院记录 |
| `nursecontent.json` | `NurseContent` | 保存护理项目 |
| `nurselevel.json` | `NurseLevel` | 保存护理级别 |
| `nurselevelitem.json` | `NurseLevelItem` | 保存护理级别与护理项目的关联关系 |
| `customernurseitem.json` | `CustomerNurseItem` | 保存客户购买或分配的护理服务 |
| `nurserecord.json` | `NurseRecord` | 保存日常护理执行记录 |
| `food.json` | `Food` | 保存膳食菜品 |
| `meal.json` | `Meal` | 保存膳食日历安排 |
| `preference.json` | `Preference` | 保存客户饮食偏好和过敏信息 |

JSON 读写由 `JsonUtil` 统一完成。DAO 调用 `JsonUtil.readList(fileName, clazz)` 读取对象列表，调用 `JsonUtil.writeList(fileName, list)` 将修改后的列表写回文件。新增数据时通常通过 `IdGenerator.nextId(fileName)` 生成新 ID，然后插入列表并写回。

系统大量使用逻辑删除。实体中常见字段 `isDeleted` 表示删除状态，`0` 表示正常，`1` 表示已删除。DAO 查询列表时一般只返回 `isDeleted == 0` 的记录，删除操作则把该字段改成 `1`，这样历史数据不会从 JSON 文件中物理消失。

## 4. 枚举类设计

枚举类位于 `com.neuedu.tms.enums` 包，主要解决“数据文件中保存数字状态，界面显示中文状态”的问题。

### 4.1 `RoleEnum`

`RoleEnum` 表示系统角色。管理员和健康管家通过 `roleId` 区分。登录成功后，`Main` 会读取当前用户的 `roleId`，如果等于管理员角色 ID，则进入 `AdminMainView`；否则进入 `StewardMainView`。

它的主要作用是避免在代码里到处写裸数字，使 `roleId=1`、`roleId=2` 的含义更清楚。

### 4.2 `Gender`

`Gender` 用于性别状态转换。实体内部用数字保存性别，展示时可以通过枚举转换成“男”“女”。这类设计让 JSON 文件更接近数据库设计，同时界面对用户保持中文可读。

### 4.3 `BedStatus`

`BedStatus` 表示床位状态：

| 状态 | 含义 |
| --- | --- |
| `FREE` | 空闲 |
| `OCCUPIED` | 有人 |
| `OUT` | 外出 |

床位状态会被多个业务模块修改。客户入住时床位从空闲变为有人；客户外出审核通过时床位从有人变为外出；外出回院登记后床位恢复为有人；客户删除或正常/死亡退住审核通过后床位恢复为空闲；床位调换时旧床位变为空闲，新床位变为有人。

### 4.4 `AuditStatus`

`AuditStatus` 用于外出申请和退住申请审核状态，通常包括已提交、同意或拒绝。外出记录 `Outward` 和退住记录 `Backdown` 都使用该状态。

### 4.5 `RetreatType`

`RetreatType` 表示退住类型，主要包括正常退住、死亡退住和保留床位。退住审核通过后是否释放床位取决于该类型：正常退住和死亡退住释放床位，保留床位不释放床位。

## 5. 实体类详细说明

实体类位于 `pojo` 包。每个实体类主要承担数据载体职责，用字段保存业务数据，用 getter、setter 提供读写入口。实体类本身不直接读写文件，也不处理复杂业务逻辑。

### 5.1 `User`

`User` 表示系统用户，包括管理员和健康管家。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 用户编号 |
| `nickname` | 用户昵称或姓名 |
| `username` | 登录账号 |
| `password` | 登录密码 |
| `sex` | 性别 |
| `phoneNumber` | 手机号 |
| `roleId` | 角色 ID |
| `isDeleted` | 逻辑删除状态 |
| `createTime` | 创建时间 |

`User` 与客户的关系主要体现在 `Customer.userId` 字段上。当管理员给客户分配健康管家时，系统会把健康管家的 `User.id` 写入客户对象的 `userId` 字段。一个健康管家可以服务多个客户，一个客户只保存一个 `userId`，因此只能绑定一个健康管家。

### 5.2 `Customer`

`Customer` 表示入住老人或客户，是系统最核心的业务实体之一。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 客户编号 |
| `customerName` | 客户姓名 |
| `customerAge` | 年龄 |
| `customerSex` | 性别 |
| `idcard` | 身份证号 |
| `roomNo` | 房间号 |
| `buildingNo` | 楼栋号 |
| `checkinDate` | 入住日期 |
| `expirationDate` | 合同到期日期 |
| `contactTel` | 联系电话 |
| `bedId` | 当前床位 ID |
| `psychosomaticState` | 身心状态或老人类型 |
| `attention` | 注意事项 |
| `birthday` | 出生日期 |
| `height` | 身高 |
| `weight` | 体重 |
| `bloodType` | 血型 |
| `userId` | 服务该客户的健康管家 ID |
| `levelId` | 护理级别 ID |
| `familyMember` | 家属信息 |
| `isDeleted` | 逻辑删除状态 |

`Customer` 与多个模块有关联：

- 与 `Bed` 通过 `bedId` 关联，表示客户当前使用哪张床位。
- 与 `BedDetail` 通过 `customerId` 关联，表示客户的床位使用历史。
- 与 `User` 通过 `userId` 关联，表示服务该客户的健康管家。
- 与 `NurseLevel` 通过 `levelId` 关联，表示客户当前护理级别。
- 与 `CustomerNurseItem` 通过 `customerId` 关联，表示客户拥有的护理服务。
- 与 `Outward`、`Backdown` 通过 `customerId` 关联，表示外出申请和退住申请。
- 与 `Preference` 通过 `customerId` 关联，表示饮食偏好。

### 5.3 `Room`

`Room` 表示房间。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 房间编号 |
| `roomFloor` | 所在楼层 |
| `roomNo` | 房间号 |

`Room` 与 `Bed` 之间通过房间号关联。床位实体中有 `roomNo`，表示该床位属于哪个房间。床位示意和入住选择房间时会用到房间数据。

### 5.4 `Bed`

`Bed` 表示床位。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 床位编号 |
| `roomNo` | 所属房间号 |
| `bedStatus` | 床位状态 |
| `remarks` | 备注 |
| `bedNo` | 床位号 |

床位状态是客户管理、外出管理、退住管理和床位调换的关键数据。系统通过 `BedStatus` 判断床位是否可入住。入住时只能选择空闲床位，调换床位时新床位也必须为空闲。

### 5.5 `BedDetail`

`BedDetail` 表示床位使用详情，也就是客户使用床位的历史记录。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 床位使用记录编号 |
| `customerId` | 客户 ID |
| `bedId` | 床位 ID |
| `startDate` | 使用开始日期 |
| `endDate` | 使用结束日期 |
| `remark` | 备注 |
| `isDeleted` | 逻辑删除状态 |

一个客户可以有多条 `BedDetail`，例如客户入住生成一条记录，后续调换床位会结束旧记录并新增新记录。当前有效记录通常表现为 `endDate` 为空且未逻辑删除。

### 5.6 `Outward`

`Outward` 表示外出申请和外出记录。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 外出记录编号 |
| `remarks` | 备注 |
| `customerId` | 客户 ID |
| `outgoingReason` | 外出原因 |
| `outgoingTime` | 外出时间 |
| `expectedReturnTime` | 预计回院时间 |
| `actualReturnTime` | 实际回院时间 |
| `escorted` | 陪同人 |
| `relation` | 陪同人与客户关系 |
| `escortedTel` | 陪同人电话 |
| `auditStatus` | 审核状态 |
| `auditPerson` | 审核人 |
| `auditTime` | 审核时间 |
| `isDeleted` | 逻辑删除状态 |

外出记录由健康管家提交，管理员审核。审核通过后，系统会根据 `customerId` 找到客户，再根据客户的 `bedId` 找到床位，把床位状态改为外出。回院登记时，再把实际回院时间写入 `Outward.actualReturnTime`，并把床位状态恢复为有人。

### 5.7 `Backdown`

`Backdown` 表示退住申请和审核记录。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 退住记录编号 |
| `remarks` | 备注 |
| `customerId` | 客户 ID |
| `retreatTime` | 退住时间 |
| `retreatType` | 退住类型 |
| `retreatReason` | 退住原因 |
| `auditStatus` | 审核状态 |
| `auditPerson` | 审核人 |
| `auditTime` | 审核时间 |
| `isDeleted` | 逻辑删除状态 |

退住申请由健康管家提交，管理员审核。审核通过后，如果退住类型为正常退住或死亡退住，系统会调用客户删除逻辑，客户被逻辑删除，当前床位释放为空闲，当前床位使用详情结束。如果退住类型为保留床位，则退住申请通过但床位不释放。

### 5.8 `NurseContent`

`NurseContent` 表示护理项目。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 护理项目编号 |
| `serialNumber` | 项目编号 |
| `nursingName` | 护理项目名称 |
| `servicePrice` | 服务价格 |
| `message` | 项目描述 |
| `status` | 状态，启用或停用 |
| `executionCycle` | 执行周期 |
| `executionTimes` | 执行次数 |
| `isDeleted` | 逻辑删除状态 |

护理项目可被护理级别引用，也可被客户单独购买。护理项目停用或删除时，需要从护理级别配置关系中移除，但不影响客户已经购买的护理服务和历史护理记录。

### 5.9 `NurseLevel`

`NurseLevel` 表示护理级别。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 护理级别编号 |
| `levelName` | 护理级别名称 |
| `levelStatus` | 级别状态 |
| `isDeleted` | 逻辑删除状态 |

护理级别本身不直接保存护理项目列表，而是通过 `NurseLevelItem` 进行关联。这种做法相当于数据库中的多对多关系中间表。

### 5.10 `NurseLevelItem`

`NurseLevelItem` 表示护理级别与护理项目之间的关系。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 关系编号 |
| `levelId` | 护理级别 ID |
| `itemId` | 护理项目 ID |

如果某护理级别包含多个护理项目，则会有多条 `NurseLevelItem` 记录。给客户设置护理级别时，系统查询该级别下所有 `NurseLevelItem`，再批量生成 `CustomerNurseItem`。

### 5.11 `CustomerNurseItem`

`CustomerNurseItem` 表示客户拥有的护理服务。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 客户护理服务编号 |
| `itemId` | 护理项目 ID |
| `customerId` | 客户 ID |
| `levelId` | 来源护理级别 ID |
| `nurseNumber` | 剩余护理次数 |
| `buyTime` | 购买或分配日期 |
| `maturityTime` | 到期日期 |
| `isDeleted` | 逻辑删除状态 |

这个实体是护理业务的核心数据之一。护理级别设置、单独购买护理项目、服务续费、日常护理扣减次数，都围绕它进行。

### 5.12 `NurseRecord`

`NurseRecord` 表示护理执行记录。

主要字段包括：

| 字段 | 含义 |
| --- | --- |
| `id` | 护理记录编号 |
| `customerId` | 客户 ID |
| `itemId` | 护理项目 ID |
| `nursingTime` | 护理时间 |
| `nursingContent` | 护理内容 |
| `nursingCount` | 护理数量 |
| `userId` | 执行护理的健康管家 ID |
| `isDeleted` | 逻辑删除状态 |

健康管家进行日常护理时会新增 `NurseRecord`，同时扣减对应客户护理项目的 `nurseNumber`。

### 5.13 `Food`

`Food` 表示膳食菜品。

主要字段包括 `id`、`foodName`、`foodType`、`isDeleted`。膳食管理模块通过它维护菜品基础数据。

### 5.14 `Meal`

`Meal` 表示膳食安排。

主要字段包括 `id`、`weekDay`、`mealType`、`foodId`、`isDeleted`。它通过 `foodId` 关联 `Food`，用于形成某天某餐次的菜单。

### 5.15 `Preference`

`Preference` 表示客户饮食偏好。

主要字段包括 `id`、`customerId`、`preferences`、`allergies`、`remark`、`isDeleted`。它通过 `customerId` 关联客户，用于记录客户喜好和过敏食物。

## 6. DAO 层详细说明

DAO 层负责把实体对象保存到 JSON 文件中，或者从 JSON 文件读取实体对象。DAO 不应该负责复杂业务规则，它只处理数据访问。

### 6.1 `UserDao`

`UserDao` 对应 `data/user.json`。

主要功能包括：

- `listAll()`：查询所有未删除用户。
- `getById(int id)`：按用户 ID 查询用户。
- `login(String username, String password)`：按账号密码查询未删除用户。
- `add(User user)`：新增用户并写回 JSON 文件。
- `update(User user)`：根据 ID 替换用户数据。
- `delete(int id)`：逻辑删除用户。
- `existsByUsername(String username)`：检查用户名是否重复。
- `listByRole(int roleId)`：按角色查询用户。
- `searchByName(String keyword)`：按昵称或姓名模糊查询。

`UserDao` 的数据会被登录、用户管理、健康管家分配等功能使用。

### 6.2 `CustomerDao`

`CustomerDao` 对应 `data/customer.json`。

主要功能包括：

- `listAll()`：查询未删除客户。
- `getById(int id)`：按 ID 查询客户。
- `add(Customer customer)`：新增客户。
- `update(Customer customer)`：更新客户。
- `existsByIdcard(String idcard)`：检查身份证号是否重复。
- `delete(int id)`：逻辑删除客户。
- `searchByName(String keyword)`：按客户姓名模糊查询。
- `listByType(String type)`：按老人类型或身心状态查询。
- `listWithoutSteward()`：查询没有分配健康管家的客户。
- `listBySteward(int userId)`：查询某健康管家负责的客户。

`CustomerDao` 是被调用最多的 DAO 之一，客户入住、退住、外出、护理、健康管家模块都会访问客户数据。

### 6.3 `BedDao`

`BedDao` 对应 `data/bed.json`。

主要功能包括：

- `listAll()`：查询所有床位。
- `getById(int id)`：按床位 ID 查询。
- `add(Bed bed)`：新增床位。
- `update(Bed bed)`：更新床位。

`BedDao` 是客户入住、床位调换、外出审核、回院登记、退住审核等模块的数据基础。

### 6.4 `BedDetailDao`

### 6.5 `OutwardDao`

- `update(Outward outward)`：更新外出记录。
- `searchByCustomerName(String keyword)`：通过客户姓名模糊查询外出记录。

### 6.6 `BackdownDao`

`BackdownDao` 对应 `data/backdown.json`。

主要功能包括：

### 6.7 `NurseContentDao`

`NurseContentDao` 对应 `data/nursecontent.json`。

- `add(NurseContent nc)`：新增护理项目。

- `delete(int id)`：逻辑删除护理项目。

### 6.8 `NurseLevelDao`

- `searchByStatus(Integer status)`：按状态查询。

### 6.14 `PreferenceDao`

`PreferenceDao` 对应 `data/preference.json`。

主要功能包括按客户 ID 查询偏好、新增偏好、更新偏好、判断客户是否已有偏好记录。它服务于客户膳食偏好管理。

### 6.15 `RoomDao`

`RoomDao` 对应 `data/room.json`。

主要功能包括查询全部房间、按楼层查询、查询所有楼层、按 ID 查询、新增、修改、删除和检查房间号是否存在。床位管理和入住选择房间时会使用该数据。

## 7. Service 层详细说明

Service 层是项目业务规则的核心。它不只是简单调用 DAO，而是把多个 DAO 操作组合成一个完整业务动作。

### 7.1 `UserService`

`UserService` 负责登录、用户管理和健康管家分配。

主要功能：

- `login(username, password)` 调用 `UserDao.login` 完成登录校验。
- `listAll()` 查询用户并排序。
- `addUser(user)` 新增用户前检查用户名是否重复，设置创建时间和未删除状态。
- `updateUser(user)` 修改用户。
- `deleteUser(id)` 逻辑删除用户。
- `listByRole(roleId)` 查询指定角色用户。
- `searchByName(keyword)` 按姓名模糊查询用户。
- `listStewards()` 查询所有健康管家。
- `assignSteward(customerId, stewardId)` 给客户分配健康管家。
- `removeSteward(customerId)` 移除客户健康管家。

关键交互：

```text
UserManageView / StewardCustomerView
  -> UserService
      -> UserDao
      -> CustomerDao
```

分配健康管家时，`UserService` 先用 `UserDao.getById` 确认被分配者存在并且角色是健康管家，再用 `CustomerDao.getById` 找到客户，把 `customer.userId` 设置为健康管家 ID，最后调用 `CustomerDao.update` 写回 `customer.json`。

### 7.2 `CustomerService`

`CustomerService` 负责客户入住、查询、修改、删除和健康管家客户列表。

主要功能：

- `listAll()` 查询所有未删除客户并按入住日期排序。
- `getById(id)` 查询单个客户。
- `addCustomer(customer)` 新增客户，检查身份证号唯一性，自动计算年龄，默认楼栋为 606。
- `updateCustomer(customer)` 修改客户并重新计算年龄。
- `deleteCustomer(id)` 逻辑删除客户，同时释放床位并结束床位详情。
- `searchByName(keyword)` 按姓名模糊查询。
- `listByType(type)` 按老人类型查询。
- `listWithoutSteward()` 查询未分配健康管家的客户。
- `listBySteward(userId)` 查询某健康管家负责的客户。

关键交互：

```text
CustomerManageView
  -> CustomerService
      -> CustomerDao
      -> BedDao
      -> BedDetailService
          -> BedDetailDao
```

删除客户时的数据同步流程：

```text
1. CustomerDao.getById(id) 查询客户
2. 将 customer.isDeleted 设置为 1
3. CustomerDao.update(customer) 写回 customer.json
4. 如果客户占用床位：
   4.1 BedDao.getById(customer.bedId) 查询床位
   4.2 bed.bedStatus = FREE
   4.3 BedDao.update(bed) 写回 bed.json
   4.4 BedDetailService.getCurrentByCustomerId(customer.id) 查询当前床位使用记录
   4.5 BedDetailService.endBedDetail(record.id) 写入结束日期
```

### 7.3 `BedService`

`BedService` 负责床位查询、床位统计、按房间查询空闲床位、床位状态修改和床位调换。

主要功能：

- `listAll()` 查询全部床位并排序。
- `getById(id)` 查询单个床位。
- `addBed(bed)` 新增床位。
- `updateBed(bed)` 修改床位。
- `updateBedStatus(id, status)` 更新床位状态。
- `listByRoomNo(roomNo)` 查询某房间床位。
- `listAvailableByRoomNo(roomNo)` 查询某房间空闲床位。
- `getStats()` 统计总床位、有人床位、空闲床位、外出床位数量。
- `swapBed(oldBedId, newBedId)` 调换床位。
- `listAllRooms()` 根据床位数据推导房间列表。

床位调换的数据同步流程：

```text
BedManageView
  -> BedService.swapBed(oldBedId, newBedId)
      -> BedDao.getById(oldBedId)
      -> BedDao.getById(newBedId)
      -> BedDao.update(oldBed: 空闲)
      -> BedDao.update(newBed: 有人)
      -> CustomerDao.listAll()
      -> 找到 bedId == oldBedId 的客户
      -> BedDetailService.getCurrentByCustomerId(customerId)
      -> BedDetailService.endBedDetail(oldDetailId)
      -> 修改 customer.bedId 和 customer.roomNo
      -> CustomerDao.update(customer)
      -> BedDetailService.addBedDetail(newDetail)
```

这个流程保证了三类数据一致：床位状态、客户当前床位、床位使用历史。

### 7.4 `BedDetailService`

`BedDetailService` 负责床位使用记录。

主要功能：

- `listByCustomerId(customerId)` 查询客户全部床位使用历史。
- `getCurrentByCustomerId(customerId)` 查询客户当前有效床位记录。
- `addBedDetail(bd)` 新增床位使用记录。
- `endBedDetail(id)` 结束床位使用记录。

它通常不会单独被用户直接感知，而是在入住、退住、删除客户、床位调换等业务中被其他 Service 调用。

### 7.5 `OutwardService`

`OutwardService` 负责外出申请、审核和回院登记。

主要功能：

- `listAll()` 查询外出记录并排序。
- `getById(id)` 查询单条外出记录。
- `addOutward(outward)` 新增外出申请。
- `updateOutward(outward)` 修改外出记录。
- `deleteOutward(id)` 逻辑删除外出记录。
- `auditOutward(id, auditStatus, auditPerson)` 审核外出申请。
- `registerReturn(id, actualReturnTime)` 登记回院。

外出审核通过的数据同步流程：

```text
OutwardManageView
  -> OutwardService.auditOutward(id, APPROVED, auditPerson)
      -> OutwardDao.getById(id)
      -> 设置审核状态、审核人、审核时间
      -> OutwardDao.update(outward)
      -> CustomerDao.getById(outward.customerId)
      -> BedDao.getById(customer.bedId)
      -> bed.bedStatus = OUT
      -> BedDao.update(bed)
```

回院登记的数据同步流程：

```text
OutwardService.registerReturn(id, actualReturnTime)
  -> OutwardDao.getById(id)
  -> 设置 actualReturnTime
  -> OutwardDao.update(outward)
  -> CustomerDao.getById(outward.customerId)
  -> BedDao.getById(customer.bedId)
  -> bed.bedStatus = OCCUPIED
  -> BedDao.update(bed)
```

### 7.6 `BackdownService`

`BackdownService` 负责退住申请、退住审核和退住记录管理。

主要功能：

- `listAll()` 查询退住记录并排序。
- `getById(id)` 查询单条退住记录。
- `addBackdown(backdown)` 新增退住申请。
- `updateBackdown(backdown)` 修改退住记录。
- `deleteBackdown(id)` 逻辑删除退住记录。
- `auditBackdown(id, auditStatus, auditPerson)` 审核退住申请。

退住审核通过的数据同步流程：

```text
BackdownManageView
  -> BackdownService.auditBackdown(id, APPROVED, auditPerson)
      -> BackdownDao.getById(id)
      -> 设置审核状态、审核人、审核时间
      -> BackdownDao.update(backdown)
      -> 判断 retreatType
          -> 正常退住或死亡退住：
              -> CustomerService.deleteCustomer(customerId)
                  -> 客户逻辑删除
                  -> 床位释放为空闲
                  -> 当前床位使用记录结束
          -> 保留床位：
              -> 不释放床位
```

### 7.7 `NurseContentService`

`NurseContentService` 负责护理项目管理。

主要功能：

- `listAll()` 查询护理项目。
- `getById(id)` 查询单个护理项目。
- `addNurseContent(nurseContent)` 新增护理项目。
- `updateNurseContent(nurseContent)` 修改护理项目。
- `deleteNurseContent(id)` 删除护理项目。
- `search(keyword, status)` 按名称和状态查询。
- `listActive()` 查询启用项目。

护理项目被护理级别配置和客户护理服务引用。业务上需要注意：护理项目停用或删除时，应该从护理级别配置中移除，但客户历史护理服务和护理记录不应该被破坏。

### 7.8 `NurseLevelService`

`NurseLevelService` 负责护理级别管理。

主要功能：

- `listAll()` 查询护理级别。
- `getById(id)` 查询护理级别。
- `addNurseLevel(nurseLevel)` 新增护理级别。
- `updateNurseLevel(nurseLevel)` 修改护理级别。
- `deleteNurseLevel(id)` 删除护理级别。
- `listActive()` 查询启用级别。
- `setLevelStatus(id, status)` 修改级别状态。
- `searchByStatus(status)` 按状态查询级别。

### 7.9 `NurseLevelItemService`

`NurseLevelItemService` 负责护理级别和护理项目之间的关系。

主要功能：

- `addItem(levelId, itemId)` 给护理级别添加护理项目。
- `removeItem(levelId, itemId)` 从护理级别移除护理项目。
- `listByLevelId(levelId)` 查询级别下的项目关系。
- `getAvailableItems(levelId)` 查询某级别还可以配置的护理项目。

它会同时访问 `NurseLevelItemDao` 和 `NurseContentDao`，用来过滤已经配置过的项目和停用项目。

### 7.10 `CustomerNurseItemService`

`CustomerNurseItemService` 负责客户护理服务设置、购买、续费、移除和状态展示。

主要功能：

- `setCustomerLevel(customerId, levelId)` 给客户设置护理级别。
- `removeCustomerLevel(customerId)` 移除客户护理级别。
- `listByCustomerId(customerId)` 查询客户已有护理服务。
- `buyItems(customerId, itemIds)` 给客户购买新的护理项目。
- `renewItem(customerId, itemId, addCount, newMaturityDate)` 续费护理项目。
- `removeItem(customerId, itemId)` 移除客户护理项目。
- `getAvailableItems(customerId)` 查询客户还能购买的护理项目。
- `getServiceStatus(customerId)` 计算服务状态。

设置护理级别的数据同步流程：

```text
NurseManageView
  -> CustomerNurseItemService.setCustomerLevel(customerId, levelId)
      -> CustomerDao.getById(customerId)
      -> customer.levelId = levelId
      -> CustomerDao.update(customer)
      -> CustomerNurseItemDao.deleteByCustomerAndLevel(customerId)
      -> NurseLevelItemDao.listByLevelId(levelId)
      -> 遍历级别下的 itemId
      -> 为每个 itemId 创建 CustomerNurseItem
      -> buyTime = 当前日期
      -> maturityTime = 当前日期 + 3 个月
      -> nurseNumber = 1
      -> CustomerNurseItemDao.add(item)
```

护理服务续费的数据同步流程：

```text
CustomerNurseItemService.renewItem(customerId, itemId, addCount, newMaturityDate)
  -> CustomerNurseItemDao.getByCustomerAndItem(customerId, itemId)
  -> nurseNumber = 原剩余次数 + addCount
  -> 如传入新到期日期，则更新 maturityTime
  -> CustomerNurseItemDao.update(item)
```

### 7.11 `NurseRecordService`

`NurseRecordService` 负责日常护理记录和护理次数扣减。

主要功能：

- `addRecord(record)` 新增护理记录，并扣减客户护理服务剩余次数。
- `listByCustomerId(customerId)` 查询客户护理记录。
- `deleteRecord(id)` 逻辑删除护理记录。

新增护理记录的数据同步流程：

```text
DailyNurseView
  -> NurseRecordService.addRecord(record)
      -> NurseRecordDao.add(record)
      -> CustomerNurseItemDao.getByCustomerAndItem(record.customerId, record.itemId)
      -> nurseNumber = nurseNumber - record.nursingCount
      -> 如果小于 0，则置为 0
      -> CustomerNurseItemDao.update(customerNurseItem)
```

这个流程保证“护理记录”和“客户护理服务剩余次数”保持一致。

### 7.12 `NurseService`

`NurseService` 是护理模块的综合服务类，封装了部分护理项目、护理级别和客户护理项目的组合操作。

主要功能包括：

- 查询、新增、修改、删除护理项目。
- 查询、新增、修改、删除护理级别。
- 查询客户护理项目。
- 设置客户护理项目。

从职责上看，它和 `NurseContentService`、`NurseLevelService`、`CustomerNurseItemService` 有一定重叠。项目中保留它可以作为护理模块的统一门面，但更清晰的做法是让不同业务分别调用更细分的 Service。

### 7.13 `FoodService`

`FoodService` 负责菜品管理。

主要功能包括查询全部菜品、按 ID 查询、新增菜品、修改菜品、逻辑删除菜品、按名称模糊查询。新增时会校验菜品名称是否重复。

### 7.14 `MealService`

`MealService` 负责膳食日历。

主要功能包括：

- 按星期查询膳食安排。
- 按星期和餐次查询。
- 新增、修改、删除膳食安排。
- `getWeekMenu()` 生成一周菜单结构。

`getWeekMenu()` 会通过 `MealDao` 读取膳食安排，再通过 `FoodDao` 查询每个 `foodId` 对应的菜品名称，最终形成按星期和餐次组织的菜单。

### 7.15 `PreferenceService`

`PreferenceService` 负责客户饮食偏好。

主要功能包括：

- `getByCustomerId(customerId)` 查询客户偏好。
- `saveOrUpdate(preference)` 如果客户已有偏好则更新，否则新增。

### 7.16 `RoomService`

`RoomService` 负责房间管理。

主要功能包括查询所有房间、按楼层查询、查询楼层列表、新增房间、修改房间和删除房间。它封装 `RoomDao`，为床位管理和入住选择房间提供基础数据。

## 8. View 层详细说明

View 层位于 `com.neuedu.tms.view` 包，是控制台交互层。View 负责打印菜单、读取用户输入、调用 Service、展示结果。项目中每个主要业务模块都有独立 View 类，符合“一类一个菜单”的设计。

### 8.1 `BaseView`

`BaseView` 是视图基类，通常提供公共输出方法，例如打印标题、分隔线、等待回车等。其他菜单类继承它，减少重复控制台输出代码。

### 8.2 `MenuItem`

`MenuItem` 是菜单项接口，子菜单类实现该接口并提供 `execute()` 方法。这样主菜单可以把不同功能视为统一菜单命令，符合命令模式思想。

### 8.3 `LoginView`

`LoginView` 负责登录交互。

流程如下：

```text
用户输入账号密码
  -> LoginView.showLogin()
      -> UserService.login()
          -> UserDao.login()
              -> user.json
  -> 登录成功后保存 currentUser
```

`Main` 会调用 `LoginView.getCurrentUser()` 获取当前登录用户，再根据角色跳转菜单。

### 8.4 `AdminMainView`

`AdminMainView` 是管理员主菜单，包含客户管理、床位管理、护理管理、外出登记管理、退住登记管理、用户管理、膳食菜品管理、膳食日历编排和退出登录。

它不直接处理具体业务，而是根据输入创建并调用子菜单：

```text
1 -> CustomerManageView
2 -> BedManageView
3 -> NurseManageView
4 -> OutwardManageView
5 -> BackdownManageView
6 -> UserManageView
7 -> FoodManageView
8 -> MealCalendarView
0 -> 返回登录
```

### 8.5 `StewardMainView`

`StewardMainView` 是健康管家主菜单，包含我的客户、日常护理、护理记录查询、外出申请、退住申请和退出登录。

它会把当前登录的健康管家用户传给子菜单：

```text
1 -> StewardCustomerView(currentUser)
2 -> DailyNurseView(currentUser)
3 -> NurseRecordQueryView(currentUser)
4 -> OutwardApplyView(currentUser)
5 -> BackdownApplyView(currentUser)
0 -> 返回登录
```

传递 `currentUser` 是为了让子菜单按照健康管家 ID 过滤客户，避免操作其他健康管家的客户。

### 8.6 `CustomerManageView`

`CustomerManageView` 是管理员客户管理菜单。

主要功能包括：

- 新增入住客户。
- 查询客户列表。
- 按客户姓名模糊查询。
- 按老人类型查询。
- 修改客户信息。
- 删除客户。

它主要调用 `CustomerService`，同时在入住选择床位时会调用 `RoomService` 或 `BedService` 查询房间和空闲床位。新增客户成功后，客户信息会写入 `customer.json`，床位状态会写入 `bed.json`，床位详情会写入 `beddetail.json`。

### 8.7 `BedManageView`

`BedManageView` 是床位管理菜单。

主要功能包括：

- 查看床位统计。
- 按房间查看床位。
- 查询空闲床位。
- 修改床位状态。
- 床位调换。

它主要调用 `BedService`。床位调换时会触发客户数据、床位数据和床位详情数据的联动。

### 8.8 `BedHistoryView`

`BedHistoryView` 负责床位使用历史查询。它主要调用 `BedDetailService` 查询客户床位使用记录，用于展示客户曾经住过哪些床位、什么时候开始、什么时候结束。

### 8.9 `OutwardManageView`

`OutwardManageView` 是管理员外出登记管理菜单。

主要功能包括：

- 查询外出申请。
- 按客户姓名查询外出记录。
- 审核外出申请。
- 登记回院。
- 删除外出记录。

审核和回院都会调用 `OutwardService`，并进一步修改床位状态。

### 8.10 `OutwardApplyView`

`OutwardApplyView` 是健康管家外出申请菜单。

它会先根据当前健康管家 ID 查询其服务客户，健康管家只能从自己的客户中选择申请对象。提交申请后，系统新增 `Outward` 记录，初始审核状态为已提交。

### 8.11 `BackdownManageView`

`BackdownManageView` 是管理员退住登记管理菜单。

主要功能包括：

- 查询退住申请。
- 按客户姓名查询退住记录。
- 审核退住申请。
- 删除退住记录。

审核通过后会根据退住类型决定是否调用客户删除逻辑释放床位。

### 8.12 `BackdownApplyView`

`BackdownApplyView` 是健康管家退住申请菜单。

它同样按当前健康管家过滤客户，避免越权提交其他客户的退住申请。提交后新增 `Backdown` 记录，等待管理员审核。

### 8.13 `NurseManageView`

`NurseManageView` 是管理员护理管理菜单，通常包括护理项目、护理级别、客户护理设置、服务关注等功能。

它会调用多个护理相关服务：

- `NurseContentService` 管理护理项目。
- `NurseLevelService` 管理护理级别。
- `NurseLevelItemService` 配置护理级别项目。
- `CustomerNurseItemService` 设置客户护理级别、购买服务、续费、移除服务、查看服务状态。

护理模块的数据交互最复杂，涉及 `nursecontent.json`、`nurselevel.json`、`nurselevelitem.json`、`customernurseitem.json` 和 `nurserecord.json`。

### 8.14 `DailyNurseView`

`DailyNurseView` 是健康管家日常护理菜单。

流程如下：

```text
当前健康管家
  -> 查询自己的客户
  -> 选择客户
  -> 查询客户护理项目
  -> 选择护理项目
  -> 输入护理时间、护理内容、护理数量
  -> NurseRecordService.addRecord()
      -> 新增护理记录
      -> 扣减客户护理服务剩余次数
```

这个菜单体现了健康管家的业务限制：只能对自己服务的客户进行护理。

### 8.15 `NurseRecordQueryView`

`NurseRecordQueryView` 负责护理记录查询。管理员可以查询客户护理记录，健康管家只能查询自己服务客户的护理记录。它主要调用 `NurseRecordService`。

### 8.16 `StewardCustomerView`

`StewardCustomerView` 是健康管家“我的客户”菜单。

它通过 `CustomerService.listBySteward(currentUser.id)` 查询当前健康管家的服务对象，只展示已绑定给该健康管家的客户。

### 8.17 `UserManageView`

`UserManageView` 是管理员用户管理菜单。

主要功能包括：

- 查询用户。
- 新增用户。
- 修改用户。
- 删除用户。
- 按角色或姓名查询。
- 分配或移除健康管家服务对象。

它主要调用 `UserService`，在分配健康管家时会间接更新客户数据。

### 8.18 `FoodManageView`

`FoodManageView` 负责膳食菜品管理，调用 `FoodService` 完成菜品新增、查询、修改和删除。

### 8.19 `MealCalendarView`

`MealCalendarView` 负责膳食日历编排，调用 `MealService` 管理一周内不同餐次的菜品安排。

## 9. 工具类详细说明

### 9.1 `JsonUtil`

`JsonUtil` 是本项目 IO 持久化的基础工具。

主要方法：

- `readList(String fileName, Class<T> clazz)`：读取 JSON 文件并转换为对象列表。
- `writeList(String fileName, List<T> list)`：将对象列表写回 JSON 文件。

所有 DAO 都依赖 `JsonUtil`。如果没有这个工具类，每个 DAO 都需要重复写文件打开、解析、关闭、异常处理等代码。

### 9.2 `IdGenerator`

`IdGenerator` 用于生成自增 ID。新增实体时，DAO 通常会调用它生成编号，避免手工输入 ID 造成重复。

### 9.3 `InputUtil`

`InputUtil` 封装控制台输入。

主要方法包括：

- `readString(prompt)` 读取字符串。
- `readInt(prompt)` 读取整数。
- `readInt(prompt, min, max)` 读取指定范围整数。
- `readOptionalInt(prompt)` 读取可选整数。
- `readDouble(prompt)` 读取小数。
- `readDate(prompt)` 读取日期。
- `readOptionalDate(prompt)` 读取可选日期。
- `readConfirm(prompt)` 读取确认选择。
- `readChoice(prompt, options)` 读取菜单选项。
- `pressEnter(prompt)` 等待回车。

它可以减少 View 层输入校验代码重复。

### 9.4 `SortUtil`

`SortUtil` 提供多个排序规则，例如按入住日期、姓名、房间床位、护理时间、角色姓名等排序。Service 层查询出列表后，会调用这些排序规则让界面显示更稳定、更符合业务习惯。

## 10. 核心业务流程与数据交互

### 10.1 登录与角色分流

```text
Main.main()
  -> LoginView.showLogin()
      -> UserService.login(username, password)
          -> UserDao.login(username, password)
              -> JsonUtil.readList("user.json", User.class)
  -> 如果 roleId 是管理员：
      -> AdminMainView.show(currentUser)
  -> 否则：
      -> StewardMainView.show(currentUser)
```

数据交互：

- 读取 `user.json`。
- 不修改数据。
- 登录成功后当前用户对象保存在内存中，用于后续权限判断。

### 10.2 客户入住

客户入住涉及客户、床位和床位详情三类数据。

```text
CustomerManageView
  -> 输入客户基础信息
  -> 查询房间和空闲床位
  -> 选择房间后绑定空闲床位
  -> CustomerService.addCustomer(customer)
  -> BedService.updateBedStatus(bedId, OCCUPIED)
  -> BedDetailService.addBedDetail(bedDetail)
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `customer.json` | 新增客户，保存床位 ID、房间号、入住日期等 |
| `bed.json` | 被选床位状态由空闲改为有人 |
| `beddetail.json` | 新增一条床位使用记录 |

业务意义：

- 保证客户当前床位可查询。
- 保证床位不会被重复入住。
- 保留床位使用历史，后续调换或退住可追溯。

### 10.3 客户删除

客户删除是逻辑删除，同时释放床位。

```text
CustomerManageView
  -> CustomerService.deleteCustomer(customerId)
      -> CustomerDao.getById(customerId)
      -> CustomerDao.update(customer.isDeleted=1)
      -> BedDao.getById(customer.bedId)
      -> BedDao.update(bedStatus=FREE)
      -> BedDetailService.getCurrentByCustomerId(customerId)
      -> BedDetailService.endBedDetail(recordId)
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `customer.json` | 客户 `isDeleted` 改为 1 |
| `bed.json` | 当前床位状态改为空闲 |
| `beddetail.json` | 当前床位使用记录写入结束日期 |

### 10.4 床位调换

床位调换要求新床位必须空闲，旧床位释放，新床位占用。

```text
BedManageView
  -> BedService.swapBed(oldBedId, newBedId)
      -> oldBed.bedStatus = FREE
      -> newBed.bedStatus = OCCUPIED
      -> 找到当前使用 oldBed 的客户
      -> 结束旧 BedDetail
      -> 修改 Customer.bedId 和 roomNo
      -> 新增新 BedDetail
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `bed.json` | 旧床位空闲，新床位有人 |
| `customer.json` | 客户当前床位 ID 和房间号更新 |
| `beddetail.json` | 旧记录结束，新记录开始 |

### 10.5 外出申请与审核

健康管家提交外出申请，管理员审核。

```text
OutwardApplyView(currentUser)
  -> CustomerService.listBySteward(currentUser.id)
  -> 选择自己的客户
  -> OutwardService.addOutward(outward)
      -> OutwardDao.add(outward)
```

管理员审核通过：

```text
OutwardManageView
  -> OutwardService.auditOutward(id, APPROVED, auditPerson)
      -> OutwardDao.update(审核状态)
      -> CustomerDao.getById(customerId)
      -> BedDao.getById(customer.bedId)
      -> BedDao.update(bedStatus=OUT)
```

回院登记：

```text
OutwardService.registerReturn(id, actualReturnTime)
  -> OutwardDao.update(actualReturnTime)
  -> BedDao.update(bedStatus=OCCUPIED)
```

### 10.6 退住申请与审核

健康管家提交退住申请，管理员审核。

```text
BackdownApplyView(currentUser)
  -> CustomerService.listBySteward(currentUser.id)
  -> 选择自己的客户
  -> BackdownService.addBackdown(backdown)
```

管理员审核通过：

```text
BackdownManageView
  -> BackdownService.auditBackdown(id, APPROVED, auditPerson)
      -> BackdownDao.update(审核状态)
      -> 如果退住类型是正常退住或死亡退住：
          -> CustomerService.deleteCustomer(customerId)
      -> 如果退住类型是保留床位：
          -> 不释放床位
```

### 10.7 护理项目与护理级别配置

护理项目和护理级别之间通过 `NurseLevelItem` 关联。

```text
NurseManageView
  -> NurseContentService 管理护理项目
  -> NurseLevelService 管理护理级别
  -> NurseLevelItemService.addItem(levelId, itemId)
      -> NurseLevelItemDao.addItem(levelId, itemId)
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `nursecontent.json` | 护理项目新增、修改、停用、删除 |
| `nurselevel.json` | 护理级别新增、修改、停用、删除 |
| `nurselevelitem.json` | 级别与项目关系新增或移除 |

### 10.8 客户护理级别设置

```text
NurseManageView
  -> CustomerNurseItemService.setCustomerLevel(customerId, levelId)
      -> CustomerDao.update(customer.levelId)
      -> CustomerNurseItemDao.deleteByCustomerAndLevel(customerId)
      -> NurseLevelItemDao.listByLevelId(levelId)
      -> 为每个护理项目生成 CustomerNurseItem
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `customer.json` | 客户 `levelId` 更新 |
| `customernurseitem.json` | 批量生成客户护理服务 |

### 10.9 日常护理

```text
DailyNurseView(currentUser)
  -> CustomerService.listBySteward(currentUser.id)
  -> 选择客户
  -> CustomerNurseItemService.listByCustomerId(customerId)
  -> 选择护理项目
  -> NurseRecordService.addRecord(record)
      -> NurseRecordDao.add(record)
      -> CustomerNurseItemDao.getByCustomerAndItem(customerId, itemId)
      -> 扣减 nurseNumber
      -> CustomerNurseItemDao.update(item)
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `nurserecord.json` | 新增护理执行记录 |
| `customernurseitem.json` | 对应护理服务剩余次数减少 |

### 10.10 健康管家服务对象分配

```text
UserManageView
  -> UserService.assignSteward(customerId, stewardId)
      -> UserDao.getById(stewardId)
      -> 校验角色是否为健康管家
      -> CustomerDao.getById(customerId)
      -> customer.userId = stewardId
      -> CustomerDao.update(customer)
```

数据变化：

| 文件 | 变化 |
| --- | --- |
| `customer.json` | 客户 `userId` 保存健康管家 ID |

健康管家的菜单通过 `CustomerService.listBySteward(currentUser.id)` 读取自己的客户，因此该字段也是权限控制依据。

### 10.11 膳食管理

膳食模块包括菜品和膳食日历。

```text
FoodManageView
  -> FoodService
      -> FoodDao
          -> food.json

MealCalendarView
  -> MealService
      -> MealDao
          -> meal.json
      -> FoodDao
          -> food.json
```

`Meal` 通过 `foodId` 关联 `Food`，因此生成一周菜单时需要同时读取膳食安排和菜品名称。

## 11. 权限与角色交互

系统中权限控制主要通过角色分流和客户归属过滤实现。

管理员权限：

- 能进入 `AdminMainView`。
- 能管理客户、床位、护理、外出、退住、用户、膳食。
- 能审核健康管家提交的外出申请和退住申请。
- 能给健康管家分配客户。

健康管家权限：

- 能进入 `StewardMainView`。
- 只能查看 `Customer.userId == currentUser.id` 的客户。
- 只能给自己的客户提交外出申请和退住申请。
- 只能给自己的客户录入日常护理。
- 只能查询自己服务对象的护理记录。

权限过滤核心字段是 `Customer.userId`。这是一种简单但有效的控制台项目权限实现方式。

## 12. 关键数据一致性规则

系统中最重要的数据一致性规则如下：

1. 客户入住时，床位必须是空闲状态。
2. 客户入住成功后，客户数据、床位状态、床位详情必须同步保存。
3. 客户逻辑删除时，当前床位必须释放为空闲。
4. 客户逻辑删除时，当前床位使用详情必须写入结束日期。
5. 外出审核通过时，客户当前床位状态改为外出。
6. 外出回院登记时，客户当前床位状态恢复为有人。
7. 退住审核通过且类型为正常退住或死亡退住时，释放床位并结束床位详情。
8. 退住类型为保留床位时，不释放床位。
9. 床位调换时，新床位必须空闲。
10. 床位调换时，旧床位空闲，新床位有人，客户当前床位信息同步更新。
11. 床位调换时，旧床位详情失效，新床位详情新增。
12. 护理项目停用或删除时，不应破坏客户历史护理服务和护理记录。
13. 给客户设置护理级别时，需要按护理级别配置批量生成客户护理服务。
14. 移除客户护理级别时，需要移除该级别带来的客户护理服务。
15. 日常护理新增记录后，需要扣减客户护理服务剩余次数。
16. 健康管家只能操作自己服务的客户。
17. 一个客户只能保存一个健康管家 ID，因此只能绑定一个健康管家。
18. 所有删除默认采用逻辑删除，保留历史数据。

## 13. 项目优点

1. 分层清晰。实体、DAO、Service、View、工具类职责分开，适合课程答辩讲解。
2. 没有依赖数据库，符合 Java IO 流持久化要求。
3. 数据结构接近数据库表设计，便于从数据库设计迁移到 JSON 文件。
4. 核心业务不是孤立增删改查，而是体现了跨表、跨文件的数据一致性。
5. 菜单拆分较细，一个主要业务一个 View 类，便于形成多级菜单。
6. 使用枚举封装状态码，降低数字状态的理解成本。
7. 使用逻辑删除，保留历史记录，符合后台管理系统常见设计。

## 14. 可改进点

1. 部分源码注释存在编码乱码，应统一以 UTF-8 重新整理注释。
2. 部分 Service 存在职责重叠，例如 `NurseService` 与多个细分护理 Service 有重复，可以后续选择一种风格统一。
3. 当前没有事务机制，多个 JSON 文件连续写入时，如果中途异常，可能出现部分写入成功、部分写入失败的情况。后续可增加备份文件或写入回滚策略。
4. 输入校验可以继续加强，例如身份证格式、手机号格式、日期先后关系等。
5. 当前数据查询以读取整个 JSON 列表再过滤为主，数据量很大时效率会下降，但对课程项目和本地控制台系统是可接受的。
6. 可增加自动化测试，覆盖入住、退住、外出、床位调换、护理扣减等关键流程。
7. 可统一状态常量和错误提示，减少 View 与 Service 中重复的中文提示。

## 15. 总结

本项目通过 Java 控制台、分层架构和 JSON 文件持久化，实现了一个较完整的养老院后台管理系统。系统以客户为核心，以床位、护理、健康管家、外出、退住、膳食为业务扩展点，通过多个实体和多个 JSON 文件模拟数据库表之间的关系。

从类的职责看，`pojo` 保存数据结构，`dao` 负责文件读写，`service` 负责业务规则和跨文件同步，`view` 负责菜单交互，`utils` 负责公共能力，`enums` 负责状态转换。从数据交互看，项目最核心的价值在于处理客户入住、床位释放、床位调换、护理服务生成、护理记录扣减、外出回院、退住审核等跨数据文件业务流程。

因此，本项目不仅能展示 Java 基础语法和 IO 文件读写能力，也能体现面向对象设计、分层设计、业务建模和数据一致性维护能力。
